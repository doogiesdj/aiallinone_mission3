목표 1

MAC 연산이란 무엇이고, AI에서 왜 중요한가

원문: MAC(Multiply-Accumulate) 연산이 무엇이고, AI에서 왜 중요한지 설명할 수 있다.

30초 답변

MAC은 두 값을 곱해서(Multiply) 누적합에 더하는(Accumulate) 연산입니다. 신경망의 뉴런 계산 Y = Σ(W × X) + B가 바로 이 곱하고 더하기의 반복이라, AI 계산량의 대부분이 MAC입니다. 그래서 MAC을 수천 개씩 동시에 처리하는 전용 칩인 NPU가 만들어졌습니다.

자세히

  • 3×3 필터 하나를 비교하는 데 곱셈 9번이 필요합니다. 25×25면 625번입니다.
  • 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 쓰므로, 고화질 이미지 한 장에도 수억 번의 MAC이 필요합니다.
  • CPU는 복잡한 명령을 순서대로 처리하는 데 강하지만, 이렇게 단순한 연산을 엄청나게 많이 반복하는 일에는 느립니다. NPU는 MAC 장치를 많이 두고 병렬로 처리해서 이 문제를 풉니다.

이 프로젝트의 근거

  • compute_mac()이 acc = 0.0에서 시작해 이중 for문으로 acc += a × b를 반복합니다. NumPy 없이 반복문으로 직접 구현했습니다.
  • 누적 변수를 0으로 초기화하지 않으면 이전 계산 값이 섞이므로, 초기화가 MAC의 첫 단계입니다.
MAC이 왜 "곱셈 따로, 덧셈 따로"가 아니라 한 단위로 묶이나요?

AI 계산에서는 곱셈 바로 다음에 항상 누적 덧셈이 오기 때문입니다. 하드웨어에서 둘을 한 장치로 묶으면 중간 결과를 따로 저장했다 꺼내는 시간이 줄어 더 빠르고 전력도 덜 씁니다.

파이썬으로 만든 이 시뮬레이터도 병렬로 계산하나요?

아닙니다. 반복문으로 한 칸씩 순서대로 계산합니다. 그래서 크기가 커지면 시간이 N²에 비례해 늘어나고, 이 한계가 바로 NPU가 필요한 이유를 보여 줍니다.

목표 2

패턴과 필터를 곱하고 더해 유사도를 구하는 원리

원문: 입력 패턴과 필터를 곱하고 더해서 유사도(점수)를 계산하는 원리를 설명할 수 있다.

30초 답변

두 배열을 겹쳐서 같은 위치의 값끼리 곱하고 모두 더합니다. 필터에서 1인 칸에 입력도 1이 있을 때만 점수가 올라가므로, 모양이 많이 겹칠수록 점수가 커집니다. 두 필터의 점수를 비교해 더 큰 쪽으로 판정합니다.

직접 눌러 보기

칸을 눌러 입력 패턴을 바꾸면 Cross 필터와 X 필터의 MAC 점수가 바로 다시 계산됩니다.

Cross 필터 (0 1 0 / 1 1 1 / 0 1 0)
X 필터 (1 0 1 / 0 1 0 / 1 0 1)
판정

이 프로젝트의 근거

  • 십자가 입력은 Cross 필터 5점, X 필터 1점으로 Cross로 판정됩니다. 미션 원문의 예시와 같은 값입니다.
  • classify_pattern()이 두 점수를 계산하고, decide_by_scores()가 epsilon 기준으로 큰 쪽을 고릅니다. 모드 1은 같은 함수로 A / B / 판정 불가를 정합니다.
  • 가운데 칸은 두 필터에 모두 1이라, 어떤 입력이든 가운데 칸은 두 점수에 똑같이 더해집니다.
입력이 0과 1이 아닌 실수여도 되나요?

됩니다. 점수는 실수(float)로 계산되고, 값이 클수록 그 칸이 점수에 더 크게 기여합니다. 그래서 동점 판정에는 부동소수점 오차를 고려한 비교가 필요해집니다(목표 4).

두 점수가 정확히 같으면 어떻게 되나요?

어느 쪽으로도 판단할 근거가 없으므로 모드 2는 UNDECIDED, 모드 1은 "판정 불가"로 표시합니다.

목표 3

data.json의 키·라벨 규칙과 라벨 정규화

원문: data.json의 "키 규칙/라벨 규칙"을 해석하고, 프로그램 내부에서 라벨을 표준화(정규화)하는 이유를 설명할 수 있다.

30초 답변

패턴 키 size_{N}_{번호}에서 N을 꺼내 size_N 필터를 고릅니다. 정답은 '+'나 'x', 필터 이름은 'cross'처럼 표기가 제각각이라, 그대로 문자열 비교하면 같은 뜻인데도 FAIL이 납니다. 그래서 들어오자마자 표준 라벨 Cross, X로 바꾼 뒤 비교합니다.

자세히

규칙원래 표기프로그램 내부
패턴 키 → 필터 선택size_13_2size_13 필터
정답(expected)'+'Cross
정답(expected)'x'X
필터 이름'cross'Cross
필터 이름'x'X

정규화는 비교하기 직전 한곳에서만 합니다. 표기를 바꾸는 규칙이 한 함수에 모여 있어야, 새 표기가 생겨도 그 함수만 고치면 됩니다.

이 프로젝트의 근거

  • normalize_label(): 앞뒤 공백을 지우고 소문자로 바꾼 뒤 '+'·'cross' → Cross, 'x' → X로 바꿉니다. 모르는 라벨은 데이터/스키마 오류로 알립니다.
  • parse_size_from_key()가 키에서 N을 꺼내고, select_global_filters()가 size_N 필터를 고릅니다.
  • data.json의 case_01~07은 정답 표기를 '+', 'cross', 'Cross', 'x', 'X'로 섞어 두었지만 모두 PASS입니다.
키의 N과 실제 패턴 크기가 다르면 어떻게 되나요?

키의 N으로 필터를 고른 뒤 크기를 비교하므로 크기 불일치로 잡힙니다. data_official_format.json의 size_5_4(키는 5, 입력은 13×13)가 이 경우이며, 그 케이스만 FAIL로 처리하고 프로그램은 계속 실행됩니다.

정규화를 출력할 때 하면 안 되나요?

비교가 먼저 일어나기 때문에 늦습니다. 비교 전에 표준 라벨로 바꿔야 PASS/FAIL이 정확하고, 콘솔 출력도 원문 요구대로 표준 라벨로 통일됩니다.

목표 4

부동소수점 오차와 epsilon 비교 정책

원문: 부동소수점 오차가 판정에 어떤 영향을 주는지, 그리고 허용오차(epsilon) 기반 비교 정책이 필요한 이유를 설명할 수 있다.

30초 답변

컴퓨터는 실수를 2진수로 근사해서 저장하므로 0.1 + 0.2가 정확히 0.3이 되지 않습니다. 이 아주 작은 차이 때문에 사실상 같은 점수가 "다르다"고 판정될 수 있습니다. 그래서 두 점수의 차이가 1e-9보다 작으면 같다고 보는 규칙을 둡니다.

이 페이지에서 계산한 결과

브라우저의 JavaScript도 파이썬과 같은 IEEE 754 배정밀도 실수를 쓰므로 결과가 같습니다.

자세히

  • ==로 비교하면 0.30000000000000004 > 0.3이 되어, 같은 점수인데도 Cross로 판정됩니다.
  • abs(a − b) < 1e-9로 비교하면 차이 5.55e-17은 "같음"이 되어 UNDECIDED로 판정됩니다.
  • 1e-9는 계산 오차(1e-17 안팎)보다는 훨씬 크고, 실제로 의미 있는 점수 차이보다는 훨씬 작습니다. 예를 들어 0과 1로 된 패턴에서는 점수 차이가 최소 1입니다. 그래서 둘을 가르는 경계로 쓰기 좋습니다.

이 프로젝트의 근거

  • EPSILON = 1e-9 상수 하나를 모든 비교(decide_by_scores(), 기대 점수 비교)에 씁니다.
  • case_08_3x3_tie_fp, size_5_3: 0.1 + 0.2 대 0.3이 UNDECIDED로 PASS.
  • case_11_err_epsilon(차이 5e-10), size_5_6(차이 5.55e-17): 동점인데 정답이 Cross로 적혀 있어 수치 비교 오류로 FAIL. 비교 정책을 확인하려고 일부러 넣은 케이스입니다.
epsilon을 더 크게 잡으면 안 되나요?

너무 크면 실제로 다른 점수까지 동점으로 처리해 판정을 잃습니다. 값의 크기가 크게 달라지는 데이터라면 상대 오차(두 값 크기에 비례한 허용오차)를 쓰는 방법도 있습니다. 이 미션은 원문 권장값 1e-9를 따랐습니다.

정수만 쓰면 이런 문제가 없지 않나요?

0과 1만 있는 패턴이라면 점수도 정수라 문제가 없습니다. 하지만 원문이 실수 점수를 허용하고, 실제 AI의 가중치도 실수이므로 비교 정책이 필요합니다.

목표 5

크기별 연산 시간 측정과 O(N²)

원문: 크기별 연산 시간을 측정하고, 패턴 크기 증가에 따른 시간 복잡도 O(N²)를 근거와 함께 설명할 수 있다.

30초 답변

N×N 행렬의 모든 칸을 한 번씩 곱하고 더하므로 연산 횟수가 정확히 N²입니다. 실제로 측정해 보면 크기가 커질수록 시간이 연산 횟수에 비례해 늘어납니다. 작은 크기에서는 함수 호출 같은 고정 비용 때문에 비례보다 조금 느리게 보입니다.

실제 측정값 (10회 반복 평균, Python 3.14.0, Windows 11)

크기연산 횟수 N²평균 시간 (ms)시간 배율연산량 배율
3×390.0011901.00x1.00x
5×5250.0019101.61x2.78x
13×131690.0082406.92x18.78x
25×256250.02677022.50x69.44x

가로축은 연산 횟수 N², 세로축은 평균 시간입니다. 점선은 시간이 연산 횟수에 정확히 비례할 때의 선입니다. 작은 크기의 점이 점선보다 위에 있는 만큼이 고정 비용입니다.

측정 방법이 중요한 이유

  • 타이머는 compute_mac() 호출만 감쌉니다. 파일 읽기, 행렬 생성, 화면 출력이 섞이면 연산 시간이 아니라 입출력 시간을 재게 됩니다.
  • 한 번 재면 운영체제 사정에 따라 값이 흔들리므로 10회 평균을 씁니다.
  • 13×13 → 25×25 구간에서 연산량은 3.70배, 시간은 3.25배로 비율이 가까워집니다. 크기가 클수록 O(N²) 추세가 잘 보입니다.

이 프로젝트의 근거

  • benchmark_mac_performance(): 행렬은 타이머 밖에서 만들고, time.perf_counter()로 MAC 구간만 10회 잽니다.
  • 보너스 실험: 2차원을 1차원 배열로 바꾸면 작은 크기에서 25~66% 빨라졌지만 51×51 이상에서는 차이가 없거나 조금 느렸습니다. 고정 비용은 줄어도 N²번의 곱셈·덧셈은 그대로이기 때문입니다.
N이 2배가 되면 시간은 몇 배가 되나요?

연산 횟수가 (2N)² = 4N²이므로 이론적으로 약 4배입니다. 고정 비용 때문에 작은 크기에서는 4배보다 덜 늘어난 것처럼 보입니다.

측정할 때마다 숫자가 다른데 괜찮나요?

정상입니다. 다른 프로그램이나 CPU 상태에 따라 절대값은 달라집니다. 중요한 것은 크기에 따라 늘어나는 비율이며, 이 비율은 반복 측정해도 비슷하게 나옵니다.

목표 6

실패 원인을 세 가지로 나눠 진단하기

원문: 실패 케이스가 발생했을 때 원인을 "데이터/스키마 문제 vs 로직 문제 vs 수치 비교 문제"로 분리해 진단하고 개선할 수 있다.

30초 답변

먼저 계산을 할 수 있는 데이터인지 봅니다. 안 되면 데이터/스키마 문제입니다. 계산은 됐는데 결과가 정답과 다르면, 동점 경계에서 갈린 경우는 수치 비교 문제이고, 그 외는 로직(또는 정답 데이터) 문제입니다. 원인이 다르면 고칠 곳도 다르기 때문에 나눠서 봐야 합니다.

진단 순서

  1. 데이터/스키마파일이나 키가 없거나, 행렬이 정사각형이 아니거나, 숫자가 아니거나, 패턴과 필터 크기가 다르면 계산 전에 멈춥니다. 고칠 곳: 데이터 파일.
  2. 수치 비교판정이나 정답 중 하나가 UNDECIDED라 동점 경계에서 엇갈렸습니다. 고칠 곳: 비교 정책(epsilon)이나 정답의 의도.
  3. 로직계산도 되고 동점도 아닌데 판정이 정답과 다릅니다. 고칠 곳: 판정 코드 또는 정답 라벨. 점수를 보고 어느 쪽이 맞는지 판단합니다.

이 프로젝트의 근거

  • 예외 클래스 세 개로 구분합니다: DataSchemaError, NumericalComparisonError, LogicError. 모두 SimulatorError를 상속하므로 모드 2는 하나만 잡아도 세 가지를 모두 처리합니다.
  • 케이스마다 따로 예외를 처리하므로 한 케이스가 실패해도 다음 케이스로 넘어가고, 끝에 실패 원인별 건수와 실패 케이스 목록을 출력합니다.
  • 예시: case_09·size_5_4(크기 불일치) → 데이터/스키마, case_10·size_5_5(Cross 패턴에 정답 x) → 로직, case_11·size_5_6(동점인데 정답 Cross) → 수치 비교.
로직 오류로 나왔는데 코드가 맞다면요?

그럴 수 있습니다. case_10은 Cross 9점, X 1점으로 판정은 맞고 정답 라벨이 틀린 경우입니다. 출력된 두 점수를 근거로 코드와 정답 중 어느 쪽을 고칠지 판단합니다.

실패가 0건이면 무엇을 설명하나요?

원문은 이 경우에도 이유를 요약하라고 합니다. 라벨 정규화로 표기 차이를 없앴고, epsilon 정책으로 부동소수점 오차를 흡수했으며, 크기 검증으로 잘못된 데이터를 계산 전에 걸러 냈기 때문이라고 설명하면 됩니다.

근거로 든 함수와 수치는 저장소 aiallinone_mission3의 main.py, npu_bonus.py, README "6. 결과 리포트"·"7. 보너스 과제"와 같습니다. 시간 측정값은 실행 환경에 따라 달라집니다.
